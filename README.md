# 동백원패스 (onepass_with_dongbakcoin)

> 결제할 때마다 "동백전을 쓸까, 어떤 카드를 쓸까?"를 고민하지 않도록, **그 순간 가장 이득인 결제수단을 규칙으로 골라 주는 원패스 결제 시뮬레이터**입니다.
> 실제 승인·정산·NFC는 없는 **모의(시뮬레이션) 프로젝트**이고, 모든 데이터는 합성 데이터입니다.

| 한눈에 보기 | |
|---|---|
| 한 줄 요약 | 동백전 + 보유 카드를 한 장(원카드)으로 묶고, 결제 순간 혜택이 가장 큰 수단을 자동 선택 |
| 판정 방식 | **규칙 기반(Rule-based)**. 결제 판정에 ML·LLM을 쓰지 않음 (같은 입력 → 항상 같은 결과) |
| 백엔드 | FastAPI + SQLAlchemy + PostgreSQL(Neon) |
| 프론트 | Next.js 고객 웹앱 |
| 분석 | 4개 시나리오 모의 결제 분석, 효과 분해(Shapley), 개인화 추천 ML(랜덤포레스트·K-means) |
| 기준 데이터 | 합성 사용자 240명 · 거래 7,540건 · 기준월 2026-06 · 데이터 v3.4 |

## 1. 프로젝트 목적

### 쉽게 말하면
동백전은 혜택이 좋지만, 쓰다 보면 **혜택이 끊기는 순간**이 옵니다. 월 캐시백 한도(50만 원)를 다 쓰거나, 잔액이 모자라거나, 가맹점 매출 구간 때문에 캐시백이 0원이 되는 순간입니다. 그러면 사람들은 결제 전에 이것저것 확인하다가, 결국 **원래 쓰던 카드로 돌아갑니다.**

이 프로젝트는 "결제 순간에 시스템이 대신 비교해서 가장 이득인 수단을 골라 주면 어떨까?"를 **시뮬레이터로 만들어 보고, 그 효과와 한계를 숫자로 확인**합니다.

### 풀려는 문제 (문제 정의)
> 동백전은 캐시백 중심의 혜택 구조와 별도 충전 과정 때문에, 이용자가 혜택·잔액·한도 변화에 따라 결제수단을 반복해서 관리해야 한다. 한도가 끝나면 원래 카드로 돌아가는 사람(도윤형)과 충전 단계 때문에 캐시백을 놓치는 사람(하은형)이 있고, 부산은행은 이 결제 전환이 카드 이용 관계에 미치는 영향을 볼 수단이 필요하다.

근거 수치 (부산연구원 현안연구 2026-03-345, 설문 2025.9 · 2,000명):

| 수치 | 값 |
|---|---|
| 가입자 중 캐시백 한도 소진 후 **다른 수단으로 이동** | 48.5% |
| 그중 신용카드로 이동 | 54.0% (가입자 대비 26.2%) |
| 결제 전 사용 가능 여부를 확인한다 | 54.8% |

### 이 프로젝트가 하는 것 / 하지 않는 것

| 하는 것 | 하지 않는 것 |
|---|---|
| 결제 순간 후보 수단 판정 + 혜택 비교 + 선택 + 선택 이유 표시 | 실제 카드 승인, 정산, NFC, 오픈뱅킹 연동 |
| 같은 결제를 "습관대로 / 원패스로" 재생해 혜택 차이 비교 | 결제 후 다른 카드로 재배정 |
| 고객 웹앱 | 실제 시민 절약액, 지역 소비 증가, 은행 수익 주장 |
| 개인화 추천 ML (먼저 챙길 고객·권할 카드의 우선순위) | 결제 판정에 ML 사용 |

> **솔직한 경계:** 원패스로 풀 수 있는 이탈은 절반 이하입니다. 미이용 이유 중 원패스가 직접 닿는 이유("다른 수단이 더 편리" 26.5 + "충전·환불 불편" 7.6 = 34.1)보다, 닿지 않는 이유("혜택 축소" 21.1 + "가맹점 적음" 17.9 = 39.0)가 큽니다 (가중 %, n=166).

## 3. 금융권 IT 4계층 반영

### 쉽게 말하면
은행 시스템은 보통 역할별로 층을 나눕니다. **창구(채널계) → 금고·장부(계정계) → 외부기관 연결(대외계) → 분석실(정보계)**입니다. 이 프로젝트도 같은 생각으로 코드를 나눴습니다. 층을 나누면 "고객 화면을 바꿔도 장부 계산은 그대로"가 되고, 문제가 생겼을 때 어느 층 문제인지 바로 찾을 수 있습니다.

| 계층 | 은행에서의 역할 | 이 프로젝트에서의 역할 | 코드 위치 |
|---|---|---|---|
| **채널계** | 고객이 만나는 창구. 요청을 받고 검증 | 고객 웹앱, API 라우터. 입력 형식 검증(pydantic), 로그인 토큰, **본인 계정만 접근**, `request_id`로 중복 요청 식별 | `frontend/`, `backend/fastapi/app/api/`, `app/schemas/` |
| **계정계** | 잔액·한도·거래를 정확히 기록하는 핵심 장부 | 지갑 잔액(충전금·캐시백·정책지원금), 카드 한도, 원장(ledger), **판정 엔진의 상태 계산** | `app/services/`, `app/repositories/`, `app/db_entities/`, `db/schema.sql`, `backend/module/onepass/engine.py` |
| **대외계** | 외부 기관·상품·정책과 연결 | 상품·혜택 규칙·동백전 정책 조회, API ↔ 엔진 연결 어댑터. **실제 승인망은 없고 모의(Mock) 경계로 대체** | `app/adapters/rule_engine_adapter.py`, `benefit_rule` · `db_policy` 테이블 |
| **정보계** | 분석·통계·보고 | 합성 데이터 생성, 4시나리오 비교, 효과 분해, ML, 결과 CSV | `backend/module/` (`compare_four_scenarios.py`, `ml/`, `results/`), `data-analysis/` |

코드 안의 층 구조 (한 요청이 지나가는 길):

```
router (요청 받기 · 권한)  →  service (업무 규칙)  →  repository (DB 읽기/쓰기)  →  db_entity (테이블)
```

> **정직한 메모:** 대외계는 "실제 연동"이 아니라 "연동 자리를 모의로 만든 것"입니다. 실제 카드사 승인·오픈뱅킹은 사업자 제휴가 필요해 범위 밖입니다.

## 4. ACID 원칙 구현

### 쉽게 말하면
ACID는 "돈이 오가는 기록이 틀리지 않게 하는 4가지 약속"입니다.

| 원칙 | 비유 | 한 줄 뜻 |
|---|---|---|
| **A**tomicity 원자성 | 계좌이체는 "출금+입금"이 둘 다 되거나 둘 다 안 됨 | 전부 성공 or 전부 취소 |
| **C**onsistency 일관성 | 장부가 항상 규칙(음수 잔액 금지 등)을 지킴 | 규칙을 어기는 상태가 저장되지 않음 |
| **I**solation 격리성 | 동시에 와도 서로 섞이지 않음 | 요청끼리 간섭 없음 |
| **D**urability 지속성 | 한 번 확정된 기록은 서버가 꺼져도 남음 | 커밋 후엔 사라지지 않음 |

### 구현 현황

| 원칙 | 어떻게 구현했나 | 코드 위치 | 한계 (솔직히) |
|---|---|---|---|
| **A** | **모의 결제**: 검증(중복·카드 소유자·가맹점) → 원장 INSERT → `commit`, 예외가 나면 `rollback`. **충전**: 지갑 잔액 증가와 원장 기록을 **한 번의 commit**으로 묶음. **시뮬레이터**: 전략마다 상태를 `deepcopy`해서 독립 실행하므로 한 전략이 다른 전략의 상태를 망가뜨리지 못함 | `payment_service.py` `create_mock_payment`, `user_service.py` `top_up`, `replay_p0.py` | 엔진의 `apply` 중간 실패를 되돌리는 코드는 없음. 대신 `evaluate`에서 **잔액·한도를 미리 검증**해서 적용 단계 실패를 막는 방식 |
| **C** | DB 제약: 외래키(FK), 값 범위 `CHECK` (예: 원장 `event_type`·`approval_status`, 카드 상태, 날짜 범위). 엔진 규칙: 금액 ≤ 0 거부, 분실·만료·비활성 카드 제외, 신용 한도·체크 잔액·동백전 잔액 부족 시 후보 제외, 중복 요청 거부 | `db/schema.sql`, `engine.py` `evaluate`/`decide` | DB 제약(`schema.sql`)과 엔진 규칙(메모리 상태)은 따로 구현되어 있어 자동으로 동기화되지는 않음 |
| **I** | **충전**: 지갑 행을 `SELECT ... FOR UPDATE`로 잠그고, 같은 `request_id` 충전은 **부분 유니크 인덱스**로 한 번만 허용(경합 시 `IntegrityError`를 잡아 기존 결과를 재생). **시뮬레이터**: `(전략, 사용자)`별 독립 상태, 시간순 처리 | `user_service.py` `_get_active_wallets(lock=True)`, `ledger_entity.py` · `db/migrations/20261103_profile_wallet_demo.sql` 의 `uq_ledger_topup_request_id` | **모의 결제는 행 잠금이 없음.** 중복은 "조회 후 삽입" 방식이라 같은 `request_id`가 정확히 동시에 오면 둘 다 통과할 수 있음 (PAYMENT에는 유니크 인덱스가 없음). 운영 단계라면 유니크 인덱스 추가 필요 |
| **D** | PostgreSQL에 `commit`된 원장은 DB가 보존. 원장은 **추가(INSERT)만** 하고 수정·삭제 코드가 없음. 시뮬레이션은 시드·정책 버전·입력 CSV를 남겨 **같은 결과를 다시 재현** | `ledger_repository.py`, `results/four_scenario_v34/` | 재현성은 "결과 파일 재현"이고, 장애 복구(백업·복제) 설계는 범위 밖 |

추가로 **멱등성**(같은 요청을 두 번 보내도 한 번만 반영)을 `request_id`로 처리합니다. 중복 결제는 HTTP 409로 거절합니다.

> **알아둘 점:** 현재 모의 결제(`POST /payments`)는 **원장에 승인 이벤트를 기록**하고, 지갑 잔액(`db_wallet`)을 차감하지는 않습니다. 잔액·한도 변화는 시뮬레이터 엔진(메모리 상태)에서 계산합니다.

직접 확인해 볼 수 있는 동작 (측정 스크립트가 함께 검사):

- 같은 `request_id` 재요청 → `DuplicatePaymentError` (거절)
- 없는 사용자로 원장 INSERT → `IntegrityError` → `ROLLBACK` → 남은 행 0건

## 5. 백엔드 기능 정리

### 쉽게 말하면
백엔드는 **"로그인한 본인에게만, 카드·잔액·결제 기록을 정확히 보여 주고 바꿔 주는 창구"**입니다. 혜택을 고르는 계산은 규칙 엔진이 하고, API는 그 엔진을 안전하게 부르고 결과를 기록하는 역할만 합니다.

| 기능 | 하는 일 | 엔드포인트 묶음 | 핵심 코드 |
|---|---|---|---|
| **인증** | 아이디·비밀번호 가입/로그인/로그아웃. 비밀번호는 PBKDF2-SHA256 해시(솔트 포함)로 저장, 로그인 토큰은 서버에 **해시만** 저장, 세션 유효기간 30일. 없는 아이디도 같은 시간 동안 해시를 계산해 "아이디 존재 여부"가 응답 시간으로 드러나지 않게 함 | `/auth/*` | `auth_service.py`, `auth_dependencies.py` |
| **본인 확인(권한)** | 경로의 `user_id`가 토큰 주인과 다르면 403. 다른 사람의 결제 상세는 존재 자체를 숨기려고 404 | 사용자별 전 경로 | `require_path_user`, `get_current_user` |
| **카드 상품·혜택 조회** | 부산은행 카드 상품 목록/상세, 상품별 혜택 규칙 조회 (읽기 전용) | `/cards/products`, `/benefits/*` | `card_service.py`, `benefit_service.py` |
| **보유 카드 관리** | 내 카드 등록/삭제/조회, 카드 간 기본 우선순위 일괄 변경 | `/users/{id}/cards*` | `card_service.py` |
| **업종별 카드 우선순위** | "카페는 A카드 먼저" 같은 사용자 설정을 저장. 같은 업종에 같은 순위·같은 카드가 중복되면 저장 거부 | `/users/{id}/category-priorities` | `category_service.py` |
| **가맹점 조회** | 가맹점 목록(페이지 단위, `limit` 1~500)·단건 조회 (QR 결제 시 가맹점 해석에 사용) | `/merchants*` | `merchant_service.py` |
| **최적 결제수단 추천** | 가맹점·금액을 받아 보유 카드별 가능 여부·예상 혜택을 계산하고 **추천 카드 1개 + 후보 전체(제외 사유 포함)** 반환. 계산은 규칙 엔진 호출 | `POST /payments/recommend` | `rule_engine_adapter.py` |
| **모의 결제** | 검증 후 원장에 승인 이벤트 기록. 중복·타인 카드·없는 가맹점 거절 | `POST /payments` | `payment_service.py` |
| **결제 내역** | 결제 상세, 사용자별 내역(최신순) 조회 | `/payments/{tx_id}`, `/users/{id}/payments` | `ledger_repository.py` |
| **지갑·충전** | 동백전 지갑 잔액(충전금·캐시백·정책지원금) 조회, 모의 충전(잔액 증가 + 원장 기록, 멱등) | `/users/{id}/wallet*` | `user_service.py` |
| **프로필** | 표시 이름 등 프로필 조회/수정 | `/users/{id}/profile` | `user_service.py` |
| **상태 점검** | DB 연결 확인 | `/health/db` | `health_router.py` |

**요청 하나가 처리되는 순서 (예: 모의 결제)**

```
POST /payments
 → 토큰 확인(로그인했나?) → 본인 확인(요청 user_id == 토큰 주인?)
 → 형식 검증(금액 > 0, 필수값)         ← 채널계
 → 중복 request_id? → 카드 존재·소유자? → 가맹점 존재?   ← 업무 규칙(service)
 → 원장 INSERT → commit (실패 시 rollback)              ← 계정계
 → 201 + 결제 결과
```

**설계 원칙**
- 라우터는 요청/응답만, 업무 규칙은 service, DB 접근은 repository에만 둡니다 (3장 계층 참고).
- 업무 오류는 service의 전용 예외(`DuplicatePaymentError` 등)로 올리고, 라우터가 HTTP 상태코드로 바꿉니다.
- 규칙 엔진은 API 코드를 복사하지 않고 `import`로 연결합니다 (`PYTHONPATH`에 `backend/module` 추가).

## 7. 결제 시뮬레이터 (규칙 기반)

### 쉽게 말하면
계산대에서 점원이 영수증을 보고 "이 카드는 한도가 찼고, 이 카드는 5% 할인이 되네요. 이걸로 할게요"라고 고르는 과정을 **if-else 규칙으로 그대로 옮긴 것**입니다. AI가 감으로 고르지 않기 때문에 **같은 입력이면 항상 같은 결과**이고, **왜 그 카드를 골랐는지 설명**할 수 있습니다.

### 판정 흐름 (`backend/module/onepass/engine.py`)

```
결제 요청
  │
  ① 요청 검사   중복 request_id? 금액 ≤ 0? 결제 경로 올바른가? 원카드 분실/정지?
  │
  ② 후보 판정   카드마다 "쓸 수 있나?"
  │             · 비활성/분실/만료 → 제외
  │             · 신용카드: 남은 한도 ≥ 결제액
  │             · 체크카드: 계좌 잔액 ≥ 결제액
  │             · 동백전: 가맹점인가? 지갑 잔액(정책지원금+캐시백+충전금) ≥ 결제액?
  │                      모자라면 연결계좌 전액 출금(캐시백 0원)으로 후보 유지, 계좌도 모자라면 제외
  ③ 혜택 계산   쓸 수 있는 카드마다 "받을 수 있는 현금 혜택(원)"
  │
  ④ 선택       혜택 큰 순 → (같으면) 사용자 업종 우선순위 → 계좌대체 동백전은 뒤로 → 카드 ID
  │
  ⑤ 상태 반영   잔액·한도·월 혜택 사용액·원장 갱신, 같은 request_id 재처리 차단
```

### 혜택 계산식

**동백전 캐시백**

```
캐시백 = 캐시백률 × min( 충전금 사용분 , 월 적용 한도(50만 원) − 이번 달 이미 적용된 금액 )
캐시백률: 연매출 10억 이하 10% / 10~30억 8% / 30억 초과 0%
```
- 정책지원금 → 캐시백 → 충전금 순으로 차감하고, **충전금으로 낸 부분만** 캐시백 대상으로 가정합니다 (확인 전 가정, 코드 `DbPolicy`에 명시).
- 한도 경계를 넘는 결제는 남은 한도만큼만 부분 적립합니다.
- 지갑이 모자라 계좌에서 전액 출금하면 캐시백은 0원입니다.

**카드 혜택** (혜택 규칙마다 계산 후 가장 큰 1개)

```
혜택 = 결제액 × 혜택률 → 건당 한도로 자름 → 월 잔여 한도로 자름 (원 단위 내림)
조건: 혜택 대상 업종/가맹점 · 최소 결제금액 · 전월 실적
```

### 이 방식을 고른 이유
- **설명 가능**: "동백전은 잔액 부족이라 0원, 카드 A는 5% 할인이라 선택" 한 줄로 설명됨
- **검증 가능**: 정답표와 1:1 대조 가능 (규칙 담당이 아닌 팀원이 정답표 작성)
- **재현 가능**: 같은 입력 → 같은 출력
- **트레이드오프**: 거래를 시간순으로 **하나씩 그때그때 최선으로 고르는 탐욕(greedy) 방식**이라 "한 달 전체 최적해"는 아님

### 테스트
- 규칙 엔진·시뮬레이션 테스트 **355개 통과**, FastAPI API 테스트 **58개 통과** (2026-11-04, 운영 DB 연결이 필요 없는 범위에서 실행)
- API 테스트 1건(`test_synthetic_csv_loader_is_idempotent_for_local_databases`)은 `backend/fastapi/data/demo_users.csv`가 저장소에 없어 실패합니다.

## 8. 시간복잡도와 처리 시간

### 시간복잡도

용어: **C** = 카드 수, **R** = 카드 1장당 혜택 규칙 수, **N** = 결제 건수

| 단계 | 하는 일 | 시간복잡도 |
|---|---|---|
| 중복·금액 검사 | `set` 조회 | O(1) |
| 후보 판정 + 혜택 계산 | 카드 C장 × 규칙 R개 확인 | **O(C·R)** |
| 최적 카드 선택 | 후보 중 최댓값 | O(C) |
| 상태 반영 | 선택 카드 찾기 + 잔액·원장 갱신 | O(C) |
| **결제 1건 전체** | | **O(C·R)** |
| **N건 연속 처리** | | **O(N·C·R)** |

쉽게 말하면, **카드가 2배 많아지면 시간도 약 2배, 결제 건수가 2배면 시간도 약 2배**로 늘어납니다 (정렬이나 반복 탐색이 없어서 급격히 커지지 않음). C와 R은 현실에서 작은 값(카드 3~6장, 규칙 수 개)이라 사실상 상수에 가깝습니다.

### 실측 결과

측정 환경: 클라우드 컨테이너(Python 3.13), 코드는 `scripts/benchmark_engine.py` · `scripts/benchmark_commit.py` 로 재현 가능. **숫자는 환경에 따라 달라집니다.**

**① 규칙 판정 (메모리, 결제 1건, 중앙값)**

| 카드 수 (카드당 규칙 3개) | 시간 |
|---|---|
| 2장 | 14.0 µs |
| 4장 | 25.5 µs |
| 8장 | 47.4 µs |
| 16장 | 90.5 µs |
| 32장 | 177.5 µs |
| 64장 | 358.1 µs |

카드 수가 2배가 될 때마다 시간도 약 2배 → **선형(O(C))** 확인. 규칙 수도 같은 식으로 선형입니다 (카드 8장 기준 규칙 1개 28.7 µs → 24개 236.1 µs).

| 연속 처리 (카드 4장 × 규칙 3개) | 총 시간 | 건당 |
|---|---|---|
| 1,000건 | 0.026초 | 25.5 µs |
| **7,540건** (분석 데이터와 같은 규모) | **0.208초** | 27.6 µs |
| 30,000건 | 0.824초 | 27.5 µs |

건수가 늘어도 건당 시간이 일정 → **O(N)** 확인.

**② 실제 거래가 반영되는 부분 (모의 결제 1건 = 검증 + 원장 INSERT + COMMIT)**

| 환경 | 중앙값 | 95% 구간 |
|---|---|---|
| SQLite (메모리) | **약 1.1 ms (0.0011초)** | 1.4 ms |
| SQLite (파일, 디스크 기록 포함) | **약 2.2 ms (0.0022초)** | 2.8 ms |

- 한 건 기준으로 **약 0.001~0.002초**입니다. 결제 판정(위 ①번)은 이보다 훨씬 짧아서(수십 µs), 시간 대부분은 **DB에 기록하고 확정(commit)하는 데** 쓰입니다.
- ⚠️ 이 값은 **로컬 임시 DB 기준**입니다. 운영 DB(PostgreSQL/Neon)는 네트워크 왕복이 더해져 더 오래 걸립니다. 배포 환경 실측은 아직 하지 않았습니다 **[미측정]**.
- ⚠️ 실제 API 추천(`/payments/recommend`)은 카드마다 상품·규칙을 DB에서 조회하므로 DB 왕복이 카드 수에 비례해 늘어납니다 (어댑터 구조상). 이 부분도 운영 환경 **[미측정]**.

## 9. 모의 결제 분석

### 쉽게 말하면
"같은 사람이 같은 물건을 사는데, **습관대로 결제하면 vs 원패스가 골라 주면** 혜택이 얼마나 달라질까?"를 합성 사용자 240명의 한 달(2026-06) 거래 7,540건으로 비교합니다. 단, **어떤 수단이 혜택을 늘렸는지(원패스의 선택 덕분인지, 잔액이 넉넉해서인지)를 분리**해서 봅니다.

### 사용한 기법

**1) 2×2 반사실(What-if) 시나리오 비교**

| | 지금 잔액 | 충분한 잔액 |
|---|---|---|
| **습관대로 결제** | S00 | S10 |
| **원패스 선택** | S01 | S11 |

- 같은 거래를 시나리오마다 **독립된 상태로 재생**합니다 (DB에 쓰지 않음).
- 습관은 사용자별 이용 방식 3유형의 **합성 가정**입니다.
- "충분한 잔액"은 이론상 상한(반사실)이며, 실제 충전 규칙은 반영하지 않았습니다.

**2) 2요인 Shapley 효과 분해** — 혜택 증가분을 "잔액 효과"와 "행동(원패스 선택) 효과"로 공정하게 나눕니다.

```
잔액 효과  = [ (S10−S00) + (S11−S01) ] / 2
행동 효과  = [ (S01−S00) + (S11−S10) ] / 2
상호작용   =  S11 − S10 − S01 + S00     (위 두 효과에 이미 반영됨, 합계에 다시 더하지 않음)
검증       :  잔액 효과 + 행동 효과 = S11 − S00   (사용자마다 코드가 확인, 어긋나면 중단)
```

**3) 민감도 분석** — 자동충전 조건을 바꿔 보는 S02 시나리오 (9칸).

### 결과 (합성 240명, 2026-06)

| 시나리오 | 총 혜택 | 1인 평균 | 동백전 결제 건수 |
|---|---|---|---|
| S00 습관 + 현재 잔액 | 1,459,931원 | 약 6,083원 | 430건 |
| S10 습관 + 충분 잔액 | 2,784,649원 | 약 11,603원 | 1,078건 |
| S01 원패스 + 현재 잔액 | 2,348,201원 | 약 9,784원 | 648건 |
| S11 원패스 + 충분 잔액 | 4,443,873원 | 약 18,516원 | 1,606건 |

| 효과 분해 (S11 − S00 = +2,983,942원) | 금액 | 비중 |
|---|---|---|
| 잔액 효과 | 1,710,195원 | 57.3% |
| 행동(원패스 선택) 효과 | 1,273,747원 | 42.7% |

**쉽게 읽기:** 원패스 선택만으로 늘어난 혜택(S01−S00)은 888,270원(+60.8%)입니다. 잔액까지 넉넉하면 효과가 훨씬 커져서(S11), **"고르는 것"과 "충전해 두는 것"이 함께 있어야 효과가 가장 크다**는 뜻입니다. 이것이 자동충전을 원패스에 포함한 근거입니다.

> 1인 평균은 위 총액을 240으로 나눈 값입니다. 모두 **합성 데이터와 합성 행동 가정에서 나온 값이며 실제 시민의 절약액이 아닙니다.** 카드 포인트는 0원으로 계산했습니다 (현금성 혜택만).

### 검증하려 한 가설 (H1~H5, 공개 통계 + 리뷰 + 설문)

| 가설 | 판정 | 핵심 근거 |
|---|---|---|
| H1 어긋난 결제(캐시백 0원)가 자주·크게 일어난다 | **존재 확인, 규모는 작음** | 캐시백 0원 결제 약 7% (가정에 따라 1~13%). 이용자 1인 월 약 200원 수준 |
| H2 결제 시점에 예측·통제가 어렵다 | **사용 가능 여부 확인은 지지, 캐시백 적용 여부는 측정 없음** | 사용 가능 여부 확인 54.8%, 방문 전 고려 61.2% |
| H3 불투명성이 우회·이탈을 만든다 | **부분 지지** (인과 검증 불가) | 한도 소진 후 다른 수단 48.5% |
| H4 자동 선택이 손실을 줄인다 | **효과 증거 없음, 요구만 있음** | → 시뮬레이터 안에서 비교 실험 |
| H5 부산은행이 운영할 수 있다 | **판단 자료 없음** | 한도 소진 후 신용카드로 이동 26.2% |

사용한 분석 방법:
- **역산**: 실제 지급된 캐시백 ÷ 일반 결제액 = 실현 캐시백률(2025.1~8월 6.11%)을 규칙상 요율(7/5/0%)과 비교해 "캐시백 0원 결제 비중"을 추정
- **신뢰구간·카이제곱 독립성 검정**: 연령별 대체 수단 차이 (χ²=66.4, df=8, p<0.001) → 18~29세는 체크, 60대 이상은 신용 비중이 높음 (하위카드 구성을 연령별로 다르게 할 근거)
- **리뷰 2,352건 분류**: "결제수단 선택이 부담"이라는 직접 언급은 8건(0.3%) → **"선택 부담" 가설 기각**, 문제 정의를 **"혜택이 끊기는 순간의 이탈"**로 수정
- **자체 설문 (n=76, 편의표본)**: 혜택 비교 "부담" 평균 2.95점·상위 2칸 40.8% (이용 상태별 차이 없음, p=0.60) → 40%는 부담을 느끼지만 다수의 문제는 아님. 기능 기대·의향 문항은 내적 일관성 α=0.84, 상관분석(ρ)으로 부담과 다른 수단 선택 빈도의 연결(ρ=0.46)을 확인. 수용성은 천장 효과가 섞인 **상한값**으로만 해석

> 한계: 인과(불투명해서 이탈했다)는 이 자료로 검증할 수 없고, 하위집단 표본이 작으면 방향만 참고합니다. 리뷰 라벨은 사람 판정 전의 1차 분류입니다.

## 10. 개인화 추천 ML

### 쉽게 말하면
시뮬레이션을 고객마다 일일이 돌리지 않아도, **결제 패턴만 보고 "이 고객은 원패스 효과가 클까? 어떤 BNK 카드를 권할까? 어떤 고객과 비슷할까?"를 빠르게 짐작**하는 모델입니다. **누구를 먼저 챙기고 어떤 카드를 권할지** 우선순위를 정하는 데 씁니다. (결제 판정에는 쓰지 않습니다.)

### 모델 3개

| # | 질문 | 모델 |
|---|---|---|
| ① | 원패스 + 충전하면 월 혜택이 얼마나 늘까? | **랜덤포레스트 회귀** |
| ② | 동백전과 함께 연결할 BNK 카드는? (6종 중 1개) | **랜덤포레스트 분류** |
| ③ | 소비 모습이 비슷한 고객은? | **K-means 군집(5묶음)** |

BNK 카드 6종: 딩딩 신용, 팟 신용, SK OIL&LPG 신용, ZipL 신용, 빵빵 체크, 어디로든 그린체크

### 단계별 설정 (`backend/module/ml/train.py`)

**STEP 1. 데이터 준비 — 고객 1명당 한 줄 (n=240)**

거래를 고객 단위로 모아 입력값 **21개**를 만듭니다.

| 구분 | 입력값 | 개수 |
|---|---|---|
| 업종별 결제 비중 | 음식점, 카페, 편의점, 마트, 병원·약국, 학원, 미용·여가, 주유, 의류, 온라인, 기타 | 11 |
| 결제 경로 비중 | 오프라인, 온라인, 간편결제 | 3 |
| 동백전 관련 | 동백전 가맹 오프라인 결제 비중, 활성 지갑 여부 | 2 |
| 규모 | 월 결제액, 결제 건수, 건당 금액 | 3 |
| 프로필 | 보유 카드 수, 연령(대표값) | 2 |

**STEP 2. 정답값 만들기**

| 모델 | 정답 |
|---|---|
| ① | 규칙 엔진 결과의 `S11 − S00` (지금 혜택 대비 "원패스 + 충분 잔액" 혜택 증가) |
| ② | 카드 6종을 하나씩 썼을 때 한 달 혜택을 규칙표(`BENEFIT_RULE`, `BENEFIT_CAP_TIER`)로 계산해 **가장 큰 카드**. 건당·월 한도·횟수·전월 실적 반영, 포인트형 혜택 0원, 동백전으로 갈 결제(가맹 + 부산 오프라인)는 제외 |
| ③ | 정답 없음 (묶기 문제) |

**STEP 3. 모델 설정**

| 모델 | 설정 |
|---|---|
| ① 회귀 | `RandomForestRegressor(n_estimators=400, min_samples_leaf=3, random_state=7)` |
| ② 분류 | `RandomForestClassifier(n_estimators=400, min_samples_leaf=2, class_weight='balanced', random_state=7)` — 카드별 표본 수 차이를 보정 |
| ③ 군집 | `StandardScaler`로 척도 맞춘 뒤 `KMeans(n_clusters=5, n_init=20, random_state=7)`. 입력은 업종·경로 비중, 동백전 비중, 건당 금액(16개)만 사용 |
| 평가 | 5겹 교차검증 (회귀 `KFold(5, shuffle)`, 분류 `StratifiedKFold(5, shuffle)`), 시드 7 고정 |

**STEP 4. 누수 방지**
- 보정 고객의 ML 값은 **교차검증 예측값**입니다. 그 고객을 보지 않은 모델이 낸 값이라 정답이 새어 들어가지 않습니다.
- 평가가 끝난 뒤 240명 전체로 다시 학습해 최종 모델을 만듭니다.

**STEP 5. 실제 사례에 적용 (T1·T4, 학습에는 사용하지 않음)**
- 엑셀 업종명을 같은 11개 묶음으로 바꿔 같은 입력값을 만들어 최종 모델에 넣습니다.
- 예상 증가액 범위 = 나무 400개 예측 중 **하위 20% ~ 상위 80%** 구간입니다.
- 카드 수·연령은 입력 자료가 없어 가정값(T1 3장·20대, T4 2장·20대)을 썼습니다.

### ML 한계 (꼭 같이 말할 것)
1. **모델이 배운 정답이 규칙 엔진 결과**입니다. 즉 "규칙 엔진을 결제 패턴만으로 근사"하는 단계이지, 실제 고객 행동(가입·재이용)을 예측한 것이 아닙니다.
2. 원패스만 썼을 때(`S01−S00`) 증가액은 **예측력이 없어(R² 0.0)** 결과로 쓰지 않았습니다.
3. 실제 사례 2명은 **학습에 쓰지 않았고** 성능 평가도 할 수 없습니다 (적용만 함).
4. 학습 데이터에 없는 업종(교통·구독·여행·통신)은 모델이 모릅니다.
5. 카드 포인트는 0원으로 계산했습니다 (현금성 혜택만).

## 11. 실행 방법

### 준비
- Python 3.12, Node.js (pnpm), PostgreSQL 연결 정보
- 저장소 루트에 `.env` 파일을 만들고 DB 주소를 넣습니다 (`.env`는 git에 올라가지 않습니다). 루트의 `.env.example`에는 아직 DB 항목이 없어 아래 내용을 직접 추가해야 합니다.

```
DATABASE_URL=postgresql+psycopg://<user>:<password>@<host>/<db>
```

### 백엔드

```bash
pip install -r backend/fastapi/requirements.txt

# DB 테이블 만들기: 스키마 → 마이그레이션 순서로 적용
psql "$DATABASE_URL" -f db/schema.sql
for f in db/migrations/*.sql; do psql "$DATABASE_URL" -f "$f"; done

# API 서버 실행 (저장소 루트에서)
PYTHONPATH=backend/fastapi:backend/module \
  uvicorn app.main:app --reload --port 8000     # http://127.0.0.1:8000/api/v1
```
- 배포 설정: `render.yaml`(Render), `vercel.json`(Vercel 서버리스 진입점)
- `psql`은 SQLAlchemy 주소(`postgresql+psycopg://`)가 아니라 일반 주소(`postgresql://`)를 씁니다.
- 현재 `scripts/init_db.py`는 import 경로가 맞지 않아 실행되지 않으므로 위 방법을 씁니다.

## 13. 한계와 주의

- **합성 데이터**입니다. 실제 고객·거래·승인이 아니며, "실제 시민 절약액", "지역 소비 증가", "부산은행 수익"을 주장하지 않습니다.
- 습관 행동(이용 방식 3유형)은 **합성 가정**이고, "충분한 잔액"은 **이론상 상한**입니다.
- 선택은 **거래별 탐욕(greedy)** 이며 월 전체 최적해가 아닙니다. 카드 포인트는 0원입니다.
- 동백전 정책 중 일부(캐시백·정책지원금 결제분의 캐시백 대상 여부, 차감 순서, 부분 적립)는 **외부 확인 전 가정**이며 코드의 `DbPolicy`에 가정으로 표시했습니다.
- 모의 결제는 원장 기록만 하고 **지갑 잔액을 차감하지 않습니다.** 결제 동시성(행 잠금·유니크 인덱스)은 충전에만 적용되어 있습니다.
- 처리 시간 중 DB 구간은 **로컬 임시 DB 기준**이고 운영 DB 실측은 아직 없습니다.
- 법률: 지역사랑상품권법·약관상 통합카드 결제의 동백전 인정 여부는 **확인되지 않은 전제**입니다 (유권해석 아님).
- 일부 폴더(`data_pipeline/`, `mock_card_verifier.py` 등)는 **빈 파일(자리만 있음)**입니다.
